HOW TO READ THE PERCENTAGES
---------------------------
Decompiled % = the published metric for the tracked code target, platform and version. Fully linked % is a separate metric; neither is overall game/asset/port completion. Different scopes are not directly comparable.
100% based on a maintainer statement is labelled as a qualitative completion claim, not invented matching-byte telemetry. Function-count percentages are labelled separately.
Not published / not verified = no trustworthy numeric percentage established in the cited evidence; it never means 0%.
Rust bindings, mod loaders, asset parsers, engines and test tools do not have a meaningful game-decomp %. Their completion % is marked NOT PUBLISHED IN CHECKED SOURCES unless an actual maintainer metric exists. Supported titles/features are described instead.
No percentages are inferred from stars, commits, release numbers, test coverage, checklist counts or the number of supported formats.
Ordering of games approximates production scale/prominence, not verified budgets. Related recompilations, disassemblies and source releases have their own appendix.
The earlier GitHub-style image used illustrative repositories and statuses; this text lists real project URLs.

RUST BINDINGS AND TOOLS — INCLUDING NON-RUST COMPANION TOOLS
=========================================================
Bindings let Rust call or represent existing native code. Parsers read/write data. A rewrite replaces behavior. A matching decomp reconstructs code against an original binary. These can support each other, but are different projects.
A useful workflow: original game + runtime bindings/loader for modding; recovered C/C++ + CXX/bindgen for gradual migration; asset parsers + a Rust engine for a new implementation. None automatically supplies missing gameplay logic.
All tooling sources/links below checked 2026-10-04. No project-wide numeric completion metric established in these checked sources.
